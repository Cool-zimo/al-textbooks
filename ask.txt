【问题 2 跟进：stdin 我核实过了，确实能用】

我拉了 al 最新的 js 读了源码，不是只看你的说明：

  runner.js:  async function execWithTests(code, tests, nsKey, stdin = null)
              stdinQueue = arr.map(v => String(v))   // 按行排队
  quiz.js:    Runner.execWithTests(ta.value, tests, nsKey, q.stdin || null)

行为正确：声明了 stdin 就按行喂，没声明维持空串（向后兼容）。

我的决定：**第 4 章的题保持预置变量，不改回 input 版本。** 理由：

  1. 第 4 章考的是 if/elif/else。改成 input 后每道题要多两行样板
     （input + int 转换），学生容易栽在这两步上 —— 而那不是本章考点，
     是第 3 章的内容。
  2. 预置变量让题干更短、更聚焦，学生一眼能看到要判断的那个数。
  3. 第 5 章开始会有真正的交互题（循环 + 菜单），那时候再用 stdin 更合适。

  如果你希望第 4 章就用上 input，告诉我，我改 + 重跑验证，成本不高。

  另外你实测的「含 input() 的题不会崩」我同意 —— 我在校验脚本里把规则改了：
    声明了 stdin  → 正常
    没声明 + int(input()) → 报错（这种真会崩）
    没声明 + 字符串拼接  → 警告（人工确认断言不依赖输入值）
  11.md 那 2 道题属于第三种，我确认过断言不依赖输入值，安全。

【本轮新发现的 2 个真 bug】

1. en/06.md 用了 JS 风格注释 `//`（已修 → `#`）
   Python 里 // 是整除运算符，那行会 SyntaxError，而且会教错注释写法。
   中文版用的是 #，只有英文版中招。已修复。
   这类问题值得警惕：翻译时容易把源语言的注释习惯带进来。

2. 05.md 的 10 条语法错误是故意的，不是 bug
   那一课主题就是「报错不是你错了」，课里全是故意写错的代码。
   校验脚本会对它报警，属正常。
