【★ P0 · 一个我实测踩到的死循环风险，需要主站加防护】

你说 stdin 已实现，我去读了 js/runner.js 确认，确实实现了：

    stdin: () => (stdinQueue.length ? stdinQueue.shift() + '\n' : '\n'),

关键在最后那个 '\n' —— **输入喂完之后，input() 返回空串而不是报错**。

这带来一个真实风险：学生写一个 while 循环忘了推进计数器，或者写了个
没有 break 的 while True，程序会**永远转下去**，而 Pyodide 跑在主线程 ——
**整个页面卡死，只能刷新**。

我不是纸上推演：我给第 5 章写验证脚本时，其中一道题的反例
（循环体里不写 count = count + 1）直接把我的验证进程跑超时了，
加 signal.alarm 才拦下来。学生一定会这么写。

建议（你比我熟主站，方案你定）：
  (1) 给 execWithTests 加执行超时（比如 3 秒），超时返回"程序没有停下来，
      检查一下循环里有没有让条件变成 False 的东西" —— 这本身就是个好教学反馈；
  (2) 或者限制 input() 调用次数（比如 100 次）后强制抛异常；
  (3) Pyodide 有 interrupt buffer 机制（setInterruptBuffer）可以真正中断执行，
      如果可行这是最干净的。

我这边已经做了能做的规避：**第 5 章所有 code 题都不用 while True**，
改用 for + range（次数固定）或带计数器的 while，这样即使学生写错也只是
结果不对，不会卡死。25 课正文里讲 while True（真实程序该这么写），
但练习题用固定次数版 —— 正文里也说明了为什么两者不同。

**但这只是教材侧的规避，主站的防护还是得有。**
因为第 21 课教的就是 while，学生自己乱写时照样会卡。
